# Phase 23: Honest Interpretation -- What Actually Moved the Needle

## The headline number

Phase 9's original checkpoint scores Recall@10/30/50 = 0.1317/0.2464/0.3216 on the test benchmark. The tuned configuration found here scores 0.1473/0.2684/0.3442 -- a real, positive gain at every K (+11.8%/+8.9%/+7.0%), verified with a single test-benchmark evaluation only after every tuning decision was locked in on a separate validation benchmark (`final_evaluation.md`). This is a genuine improvement to phase 9's mechanism, not a benchmark artifact or a validation-only illusion -- the test-benchmark gain (+11.8% at K=10) is close to, even slightly larger in relative terms than, the validation-benchmark gain (0.1410 -> 0.1600, +13.5%), so the tuning transferred honestly rather than overfitting to the validation set.

## What actually moved the needle, ranked by how much it mattered

**1. Fixing the checkpoint selection criterion was the single biggest lever, and it isn't a hyperparameter at all.** Phase 9's original training loop selected its saved checkpoint by validation loss, and that loss was best at epoch 0 -- every subsequent epoch's validation loss was strictly worse, so early stopping (patience=5) fired at epoch 5 and the epoch-0 weights were what got saved and cited everywhere in this project since (`week3/phase9_polyvore_compatibility/models/training_curves.json`, `model_a_random_negs` curve: val_loss 5.2566 at epoch 0, rising every epoch after). But this phase's very first smoke test -- two epochs, phase 9's *exact original* lr/bs/tau/wd -- showed Recall@10 rising from 0.1410 (epoch 0, matching phase 9's real number) to 0.1467 (epoch 1). Every later stage confirmed the same shape: Recall@10 keeps improving for several epochs past the point where validation loss says to stop, then genuinely peaks and declines (step 5's 60-epoch run: peak at epoch 4, 0.1564, then a sustained decline through epoch 19). Phase 9 was never given the chance to reach its own real optimum, not because it lacked epochs or patience, but because the metric used to decide "when to stop and what to keep" was the wrong one. This project has flagged the val-loss-vs-Recall@K decoupling as a lesson before (phases 14, 14b, 16d) but phase 9 itself -- cited as the project's best result in every comparison since -- had never actually been re-checked against this lesson until now.

**2. Batch size mattered, consistently.** bs=256 beat bs=128 and bs=64 at every learning rate tested in the step 3 grid (9/9 comparisons). This is a sensible, mechanistic result for an in-batch-negative contrastive loss: a bigger batch means more in-batch negatives per anchor, which is a real signal quality improvement, not a fragile hyperparameter accident. Learning rate mattered less once batch size was fixed -- 0.0005 and 0.001 landed close together at bs=256 (0.1534 vs 0.1535), while 0.002 was worse everywhere. lr=0.001 was kept as the winner mainly because it matched phase 9's own original learning rate almost exactly (making the comparison to phase 9 cleaner) while being statistically indistinguishable from 0.0005 here.

**3. Temperature (tau) gave a further real gain, but the sweep did not find its ceiling.** tau=0.15 beat phase 9's original tau=0.07 by a clear margin (0.1564 vs 0.1535 at matched lr/bs), and Recall@10 rose monotonically across the entire tested range from 0.03 to 0.15 -- there is no sign of a peak inside the tested grid. This is an honest gap in this phase's own work: the temperature sweep should be read as "0.15 beats 0.07, and it's not obviously done improving," not as "0.15 is the optimal temperature." A natural, cheap follow-up (tau in {0.2, 0.25, 0.3}) was not run here, per the phase's own step budget, and is flagged as the most promising unexplored direction if this thread is revisited.

**4. Weight decay = 0.0 gave a small further gain, worth taking seriously but not overselling.** Dropping weight decay to 0 beat phase 9's original 1e-5 by 0.1600 vs 0.1564 at matched lr/bs/tau -- a real, non-trivial margin, and larger than the spread the R (random negatives) sweep produced at fixed weight decay. But this is based on one run per configuration, no repeated-seed variance estimate, so it should be read as "the best-observed setting," not as a statistically confirmed effect. Given the tiny dataset-relative model size (a 2-layer, ~460K-parameter MLP on frozen 768-d features, no image encoder to regularize), a near-zero weight decay being preferable is plausible on priors, not surprising.

**5. R=8 (phase 9's own original random-negative count) was already the best choice -- this is the one place phase 9's original setting was NOT the problem.** Across every weight-decay value tested in step 6, R=8 beat both R=4 and R=12. This is worth stating plainly: not every one of phase 9's original choices needed fixing. The negative-sampling count was fine; the learning-rate/batch-size/temperature/weight-decay combination and, above all, the checkpoint-selection criterion were what needed fixing.

## What this means, plainly

Hyperparameter tuning meaningfully strengthened phase 9's existing mechanism -- a real 7-12% Recall@K gain at every K, confirmed once and honestly on the actual test benchmark, with no architecture change. But the single most important lesson from this phase is not "use lr=0.001/bs=256/tau=0.15/wd=0.0" as a specific recipe -- it's that **this project's own repeatedly-learned lesson about validation loss not predicting real retrieval quality had never actually been applied to phase 9 itself**, the one result everything else in this project has been compared against. Phase 9's original checkpoint was quietly leaving real, measurable Recall@K on the table (roughly a third of this phase's total gain shows up in the very first two-epoch smoke test, before a single hyperparameter value was even changed) simply because nobody had re-selected its checkpoint by the right metric. The hyperparameter values found here are real and worth adopting, but they are the second-order finding; the first-order finding is procedural.

## Updated reference point for future work

**New best configuration**: lr=0.001, batch_size=256, weight_decay=0.0, tau=0.15, R=8 (H=0), selected by validation-benchmark Recall@10 (best at epoch 4-5, not by validation loss). Test-benchmark Recall@10/30/50 = 0.1473/0.2684/0.3442, saved at `week4/phase23_hyperparameter_tuning/models/final_tuned.pt`. This is now the strongest result in the project, superseding phase 9's original 0.1317/0.2464/0.3216 everywhere that number was previously cited as the project's best -- see the `PROJECT_MEMORY.md` update accompanying this phase.

## What wasn't done here (explicitly out of scope, not an oversight)

Per this phase's own "do not do yet" instruction: no architecture change, no scale change, no backbone change. The temperature sweep's un-bracketed optimum (point 3 above) is the most obvious immediate follow-up within this same scope; architecture/scale tuning is the next logical phase in this project's own stated sequence, not attempted here.
